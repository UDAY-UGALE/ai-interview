# Deploying

Three things deploy independently: the **backend** (container), the
**website** (static files), and the **client** (a Windows download).

For how the pieces fit together and why the client is desktop software, see
[ARCHITECTURE.md](ARCHITECTURE.md).

---

## Backend on Render

### Service settings

| Setting | Value |
| --- | --- |
| Service type | Web Service |
| Runtime | Docker (`./Dockerfile`) |
| Build command | *none* — the Dockerfile is the build |
| Start command | *none* — `CMD` in the Dockerfile: `uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000} --workers 1 --ws-ping-interval 20 --ws-ping-timeout 20` |
| Health check path | `/health` |
| Plan | Free |
| Region | Singapore (closest free region to India) |
| Instances | **1** — see the scaling note below |

All of this is already declared in [render.yaml](render.yaml); the table is
for when you deploy somewhere without a blueprint.

### Environment variables

Required:

| Variable | Value |
| --- | --- |
| `GROQ_API_KEY` | your key — **secret** |
| `APP_AUTH_TOKEN` | long random string — **secret**, generated by the blueprint |

Recommended on a free instance:

| Variable | Value | Why |
| --- | --- | --- |
| `SESSION_LOG_ENABLED` | `false` | ephemeral filesystem — logs are wiped on every restart anyway |
| `SESSION_STORE_BACKEND` | `memory` | no external dependency; correct for one instance |
| `APP_VERSION` | e.g. `0.1.0` | so `/version` tells you which build is live |

Optional: `ANSWER_PROVIDER`, `ANSWER_MODEL`, `STT_PROVIDER`, `STT_MODEL`,
`VISION_PROVIDER`, `VISION_MODEL`, `CORS_ALLOW_ORIGINS`, and the tuning
variables. Full list with defaults: [.env.example](.env.example).

### Steps

1. **Push.** Confirm `.env` is not in the commit — it is gitignored, keep it
   that way.
2. **Render → New → Blueprint →** select the repository. It reads
   `render.yaml` and creates both the backend and the website.
3. **Paste `GROQ_API_KEY`** when prompted. Leave the other key fields blank
   unless you use those providers.
4. **Copy `APP_AUTH_TOKEN`** from the service's Environment tab. That is what
   clients present.
5. **Verify** (below) before handing the URL to anyone.

### Scaling note

Keep this at one instance and one worker. The session store and the answer
hub are both in-process, so a client's audio socket and its answer socket
must reach the same process. Two workers put them in different ones and
answers silently never arrive. Scaling out means `SESSION_STORE_BACKEND=redis`
**and** moving the answer hub to pub/sub — until then, scale vertically.

## Website

The blueprint deploys `web/` as a Render Static Site. It is plain HTML with
no build step, so it deploys anywhere: S3 + CloudFront, Azure Static Web
Apps, Netlify, GitHub Pages, any CDN.

It makes no request to the backend, which is the point — the landing page and
the download link keep working while the backend is asleep or redeploying.

Before going live, edit:

- `web/index.html` — product name and copy
- `web/download.html` — the `href` on the download button, to wherever you
  host the release zip
- `web/privacy.html`, `web/terms.html` — every `[bracketed]` placeholder.
  **Both are drafts and need a lawyer's review before you publish them**,
  especially if users are in the UK/EU, California, or India.

## Client

### Build a release

```powershell
pip install -r requirements-client.txt
pip install pyinstaller
powershell -File scripts\build_client.ps1
```

Produces `dist\InterviewCopilot-windows-<version>.zip` containing both
executables, a config template, `start.bat`, and a README. Upload it to
wherever `web/download.html` points — object storage or a GitHub release,
**not** the backend repository.

To pre-fill the server address so the download needs no setup:

```powershell
powershell -File scripts\build_client.ps1 -ApiUrl "https://your-backend.onrender.com"
```

The token is deliberately never baked in: it would mean rebuilding on every
rotation, and a token inside a widely distributed binary is not a secret.

### Configure a client

`interviewcopilot.json`, in the same folder as the executables:

```json
{
  "api_url": "https://your-backend.onrender.com",
  "token": "the APP_AUTH_TOKEN",
  "session_id": "one-per-person"
}
```

Precedence is CLI flag → environment variable → config file → `http://127.0.0.1:8000`.
So `INTERVIEW_API_URL` / `INTERVIEW_TOKEN` / `INTERVIEW_SESSION_ID` work for
scripted setups, flags win for one-off overrides, and running from source
with nothing set still points at localhost.

**Give every person a different `session_id`.** Sessions are keyed by it:
two clients sharing one would share a résumé, a history, and each other's
answers.

## Verifying

### Locally, before you deploy

Run the exact image Render will run:

```powershell
docker build -t interviewcopilot .
docker run --rm -p 8000:8000 --env-file .env -e APP_AUTH_TOKEN=localtest interviewcopilot
```

```powershell
# open, no token needed
Invoke-RestMethod http://127.0.0.1:8000/health

# should report auth_required = True
Invoke-RestMethod http://127.0.0.1:8000/version

# should FAIL with 401
Invoke-RestMethod http://127.0.0.1:8000/models

# should return the catalog
Invoke-RestMethod http://127.0.0.1:8000/models -Headers @{ Authorization = "Bearer localtest" }
```

Then the client against it:

```powershell
python client\test_loopback_stream.py --ws-url ws://127.0.0.1:8000/ws/audio --token localtest
python client\overlay_app.py --api-url http://127.0.0.1:8000 --token localtest
```

Two offline suites need no API key, no microphone, and no server:

```powershell
python client\test_pipeline_e2e.py             # segmentation → STT → gate → answer
python client\test_question_gate_scenarios.py  # question-detection edge cases
```

### On Render, after deploying

1. **Health** — `Invoke-RestMethod https://<app>.onrender.com/health` → `status=ok`.
   First call after idle takes ~50s; that is the cold start, not a fault.
2. **Auth** — `/version` shows `auth_required: True`, and `/models` without a
   token returns 401. *If it returns data instead, your URL is open to
   anyone who finds it. Stop and fix that first.*
3. **Websocket** — `python client\test_answer_stream.py --ws-url wss://<app>.onrender.com/ws/answers --token <token>`
   should print a `ready` frame. A 403 means the token is wrong; a hang means
   websockets are not reaching the service.
4. **Audio capture** — start the capture client and play any audio. The level
   meter must move. If it stays flat, `--list-devices` and pick the right
   output device with `--device N`.
5. **Detection + STT** — speak a question. The capture console prints a
   `[transcript]` line within a second or two of you stopping.
6. **Gate + LLM** — the overlay shows the question, then answer text streaming
   in. First token typically 1.5–2.5s after you stop speaking, over the
   internet.
7. **Overlay behaviour** — start a screen share of your whole desktop and
   confirm the overlay is absent from the shared view.
8. **Context** — drop a résumé PDF on the overlay, ask something from it, and
   confirm the answer uses specifics only that PDF could have supplied.
9. **Screen analysis** — trigger it with something on screen and confirm the
   response arrives through the same overlay.

## Moving to AWS

Nothing in `app/` changes. The image is the deliverable.

1. `docker build` → push to **ECR**.
2. Run on **ECS Fargate** (or App Runner, which is fewer moving parts and
   handles TLS itself). One task, 0.5 vCPU / 1 GB is ample.
3. **ALB** in front for TLS and a domain. Health check → `/health`.
   **Raise the target group's idle timeout above 3600s** — the default 60s
   kills an interview's websocket mid-call.
4. Secrets in **Secrets Manager** or SSM Parameter Store, injected as env
   vars in the task definition. Same variable names.
5. Website → **S3 + CloudFront**. Client zips → the same bucket.
6. Logs → stdout is already picked up by **CloudWatch**; leave
   `SESSION_LOG_ENABLED=false`.
7. Only if you scale past one task: **ElastiCache** and
   `SESSION_STORE_BACKEND=redis`, plus the answer-hub pub/sub work.

Avoid API Gateway and Lambda for `/ws/audio` — the 29-second request cap and
the function execution model are incompatible with an hour-long stream.

## Moving to Azure

1. `docker build` → push to **ACR**.
2. Run on **Container Apps**. It terminates TLS, gives you a hostname, and
   supports websockets without extra configuration. Set min replicas to 1
   (scale-to-zero reintroduces cold starts) and max replicas to 1 until the
   Redis work is done.
3. Secrets in **Key Vault**, referenced from the container app's secret
   store. Same variable names.
4. Website → **Azure Static Web Apps**. Client zips → **Blob Storage**,
   optionally behind Azure CDN.
5. Logs → stdout, collected by **Log Analytics**.
6. Only if you scale out: **Azure Cache for Redis**.

## Known limitations

**Render Free is for development, demo and validation — not production.**

| Limitation | Effect |
| --- | --- |
| Sleeps after 15 min idle | ~50s cold start. Hit `/health` a minute before you need it. |
| 512 MB RAM, 0.1 CPU | Fine for this workload (Groq does the heavy lifting), but no headroom for `STT_PROVIDER=faster_whisper`, which needs 1–2 GB. |
| Ephemeral filesystem | Session logs are wiped on every restart and redeploy. Keep `SESSION_LOG_ENABLED=false`. |
| Single instance | Required by the in-process session store and answer hub, not just a free-tier limit. |
| No SLA | It restarts when Render feels like it. Do not schedule anything that matters on it. |

**Application limitations, independent of host:**

- **Shared rate limits.** Every client draws on one provider key. The
  README's ~2–3 questions/minute on an 8,000 TPM free tier is the *total*
  across everyone connected. Concurrent users need a paid tier or a key each.
- **One shared token.** Access control is a single secret, not user accounts.
  It cannot be revoked per person; rotating it invalidates every client. Real
  accounts need a user store, which does not exist yet.
- **Windows only.** The overlay's capture exclusion and the loopback capture
  are both Win32. There is no macOS or Linux client.
- **No auto-update.** Clients are a zip. A new version means telling people
  to download it again. The version is in `VERSION` and reported by
  `/version`, which is the hook a future updater would use.
- **Answer quality depends on the résumé.** With thin context the model
  hedges. This is a data problem, not a deployment one.
